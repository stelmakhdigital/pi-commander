## Цель

Исправить ошибки, улучшить архитектуру проекта и разработать приоритетные новые возможности. Работа должна выполняться автономным конвейером агентов без вмешательства человека до завершения задач или прямой остановки пользователем.

Проект необходимо предварительно изучить. На основании текущего состояния кода агенты должны определить следующие наиболее важные доработки и выполнять их по приоритету.

## Критерии приёмки

- [ ] Сформирован и поддерживается актуальный план следующих задач.
- [ ] Все изменения соответствуют архитектуре проекта и существующим соглашениям.
- [ ] Для каждого изменения добавлены или обновлены автоматические тесты.
- [ ] Тесты выполнены до и после вмешательства.
- [ ] Для изменений UI сохранены скриншоты до и после.
- [ ] Каждая завершённая итерация зафиксирована отдельным git-коммитом.
- [ ] Коммиты имеют краткие описательные сообщения.
- [ ] Worker проверил работу всех подагентов и принял итоговый результат.
- [ ] После интеграции прошли полный набор тестов и проверки сборки.
- [ ] В корневую ветку не попали секреты, пароли, временные файлы и служебные файлы агентов.
- [ ] Следующая задача назначена planner-агентом автоматически.

## Референсы

- Текущая архитектура, код, тесты и документация проекта.
- `worker_roles.md` и правила работы подагентов.
- Публичные архитектурные примеры, найденные агентами самостоятельно.
- Принципы разделения ответственности, dependency inversion, явных интерфейсов, тестируемости и наблюдаемости.

## Правила

- `w-<name_project>` (worker) выполняет задачи по планам и инструкциям.
- `p-<name_project>` (planner) поставляет следующую цель и задачу по приоритету после завершения текущей.
- `j-<name_project>` (judge) проверяет выполнение задачи и критерии приёмки.
- Все три агента могут создавать собственных подагентов для распараллеливания работы.
- Worker обязан прочитать `worker_roles.md` и запустить отдельного подагента в tmux для каждой активной роли.
- Количество подагентов должно точно совпадать с количеством активных ролей в `worker_roles.md`.
- Worker управляет подагентами и полностью отвечает за их готовую работу.
- Каждый подагент работает только в собственной ветке `agent/<role>/<iteration>`.
- Ветка создаётся от корневой ветки, актуальной на момент запуска итерации.
- Подагент не изменяет корневую ветку напрямую.
- Подагент может выполнять локальные коммиты, но не имеет права самостоятельно пушить в корневую ветку или удалённый репозиторий.
- Перед передачей результата подагент обязан проверить, появились ли новые коммиты в корневой ветке.
- Если корневая ветка изменилась, подагент обязан выполнить `git pull`, сделать merge корневой ветки в свою ветку, разрешить конфликты и повторно выполнить тесты.
- Только worker принимает решение о merge в корневую ветку и push в удалённый репозиторий.
- Worker обязан проверить код, историю коммитов, тесты, критерии приёмки и отсутствие незакоммиченных изменений.
- Каждый шаг фиксируется коммитом с кратким описанием сделанного.
- Push выполняется только после успешной проверки и интеграции.
- При проверке кода тесты запускаются до и после вмешательства.
- При изменении UI обязательно делать скриншоты до и после соответствующих участков.
- Файлы `memory*`, `task*`, `agents*`, `worker_roles.md`, скриншоты, секреты, пароли, логи и временные файлы добавляются в `.gitignore`, если они являются рабочими артефактами агентов.
- Агенты не спрашивают человека. При неоднозначности они принимают безопасное решение, фиксируют допущение и продолжают работу.
- Работа может быть остановлена только прямым требованием пользователя.

### Git-протокол

1. Worker определяет текущую корневую ветку `<root-branch>`.
2. Каждый подагент создаёт свою ветку от актуальной `<root-branch>`.
3. Подагент выполняет работу и создаёт локальные коммиты.
4. Перед передачей результата подагент получает актуальное состояние `<root-branch>`.
5. При изменениях в `<root-branch>` подагент делает merge `<root-branch>` в свою ветку.
6. Подагент разрешает конфликты и повторно запускает тесты.
7. Worker проверяет результат и выполняет merge принятой ветки в `<root-branch>`.
8. Worker запускает интеграционные и регрессионные проверки.
9. Только worker принимает решение о push.

## Границы

- Не выполнять действия вне репозитория без необходимости.
- Не удалять рабочие данные без резервной копии или явного обоснования.
- Не менять публичные контракты без проверки совместимости.
- Не добавлять зависимости без анализа необходимости и влияния.
- Не коммитить секреты, пароли, токены, ключи и персональные данные.
- Не считать задачу выполненной только по факту успешной компиляции.
- Не передавать человеку вопросы, которые агенты могут решить самостоятельно.
