# Worker roles

Этот файл определяет обязательные роли подагентов для текущей итерации.

Worker обязан запустить по одному подагенту на каждую активную роль. Количество активных ролей равно количеству подагентов, которые должны быть запущены в tmux.

## Общие правила ролей

- Каждая роль выполняется отдельным подагентом.
- Один подагент не может одновременно выполнять несколько ролей.
- Каждый подагент работает в собственной git-ветке.
- Ветка подагента создаётся от корневой ветки, актуальной на момент запуска.
- Подагент коммитит изменения локально.
- Подагент не выполняет push в корневую ветку.
- Worker принимает решение о merge и push.
- Перед передачей результата подагент обязан проверить актуальность корневой ветки, выполнить pull и merge корневой ветки в свою рабочую ветку, разрешить конфликты и повторно запустить тесты.
- Worker проверяет результат каждого подагента до интеграции.

## Роль: backend

### Идентификатор

`backend`

### Назначение

Разработка серверной части, бизнес-логики, API, фоновых задач, интеграций и хранения данных.

### Обязанности

- Анализировать существующую backend-архитектуру.
- Реализовывать серверную логику и API.
- Соблюдать соглашения проекта.
- Добавлять и обновлять unit-, integration- и contract-тесты.
- Проверять ошибки, конкурентный доступ, таймауты и отмену операций.
- Документировать изменения API и миграций.
- Проверять совместимость с frontend и другими сервисами.

### Критерии готовности

- Код собирается без ошибок.
- Новая функциональность покрыта тестами.
- Существующие тесты не сломаны.
- API и схемы данных совместимы с системой.
- Изменения оформлены локальными git-коммитами.
- Worker получил описание изменений, тестов и ограничений.

## Роль: frontend

### Идентификатор

`frontend`

### Назначение

Разработка пользовательского интерфейса, клиентской логики, состояний, навигации и взаимодействия с API.

### Обязанности

- Анализировать существующие UI-паттерны.
- Реализовывать пользовательские сценарии.
- Подключать и проверять API.
- Соблюдать дизайн-систему и существующие компоненты.
- Добавлять unit-, integration- и e2e-тесты.
- Проверять состояния загрузки, ошибок, пустых данных и повторных запросов.
- При изменении UI делать скриншоты до и после доработки.

### Критерии готовности

- Интерфейс корректно работает в предусмотренных сценариях.
- Нет ошибок в консоли и сетевых запросах.
- Тесты проходят.
- Скриншоты до и после сохранены, если изменялся UI.
- Изменения оформлены локальными git-коммитами.
- Worker получил описание изменений, тестов и ограничений.

## Роль: tester

### Идентификатор

`tester`

### Назначение

Проверка качества, регрессии, тестового покрытия и соответствия критериям приёмки.

### Обязанности

- Анализировать критерии приёмки из `task.md`.
- Составлять план проверок.
- Запускать существующие тесты до и после изменений.
- Добавлять недостающие тесты.
- Проверять негативные сценарии и граничные случаи.
- Проверять совместимость затронутых компонентов.
- Фиксировать дефекты и передавать их worker.

### Критерии готовности

- Все обязательные проверки выполнены.
- Результаты тестов зафиксированы.
- Регрессии отсутствуют либо описаны.
- Недостающие тесты добавлены.
- Найденные проблемы имеют шаги воспроизведения.

## Роль: reviewer

### Идентификатор

`reviewer`

### Назначение

Независимое ревью архитектуры, безопасности, читаемости и сопровождаемости кода.

### Обязанности

- Проверять изменения относительно `task.md`.
- Искать архитектурные дефекты и нарушение границ ответственности.
- Проверять ошибки и потенциальные проблемы безопасности.
- Проверять читаемость и тестируемость кода.
- Проверять отсутствие лишних изменений и секретов.
- Формировать список обязательных и необязательных исправлений.

### Критерии готовности

- Проведено независимое ревью.
- Замечания классифицированы по приоритету.
- Блокирующие замечания устранены либо явно приняты worker.
- Результаты ревью переданы worker.

## Роль: devops

### Идентификатор

`devops`

### Назначение

Проверка сборки, CI/CD, контейнеров, окружения, конфигурации и эксплуатации.

### Обязанности

- Проверять команды сборки и запуска.
- Проверять Docker/Compose, CI/CD и deployment-конфигурацию.
- Проверять миграции, переменные окружения и секреты.
- Проверять логирование, health checks и graceful shutdown.
- Искать проблемы воспроизводимости и совместимости окружений.
- Обновлять эксплуатационную документацию.

### Критерии готовности

- Сборка и запуск воспроизводимы.
- Конфигурация не содержит секретов.
- CI/CD не сломан.
- Health checks и миграции работают.
- Изменения оформлены локальными git-коммитами.

## Роль: docs

### Идентификатор

`docs`

### Назначение

Создание, заполнение, актуализация и проверка технической документации проекта в соответствии с текущим кодом, API, архитектурой и эксплуатационными сценариями.

### Область ответственности

Подагент `docs` отвечает за:

- пользовательскую документацию;
- документацию для разработчиков;
- описание архитектуры;
- API и интеграционные контракты;
- инструкции по установке, запуску и эксплуатации;
- changelog и release notes;
- примеры конфигурации;
- описания CLI-команд;
- troubleshooting и типовые сценарии диагностики;
- актуальность ссылок, команд, путей и примеров кода.

### Обязанности

- Изучить `task.md`, текущий код, тесты и существующую документацию.
- Найти документацию, которая стала устаревшей из-за изменений.
- Добавить отсутствующую документацию для новой функциональности.
- Обновить README, guides, API reference, архитектурные документы и эксплуатационные инструкции.
- Проверить, что команды, пути, переменные окружения и примеры соответствуют текущему проекту.
- Описать ограничения, известные проблемы и обратную совместимость.
- Синхронизировать документацию с фактическим поведением кода.
- Не добавлять неподтверждённые сведения и не описывать нереализованные возможности как готовые.
- Проверять внутренние ссылки и ссылки на файлы.
- Запускать доступные проверки документации, линтеры и сборку документации.
- При наличии исполняемых примеров проверять их выполнение.
- Передать worker список обновлённых документов и результаты проверок.

### Категории документации

Документацию следует распределять по четырём категориям:

- `tutorials` — пошаговое обучение для нового пользователя.
- `how-to` — инструкции для решения конкретной задачи.
- `reference` — точное описание API, CLI, конфигурации и параметров.
- `explanation` — архитектура, принципы, ограничения и обоснование решений.

### Критерии готовности

- Документация соответствует фактическому состоянию кода.
- Новая публичная функциональность описана.
- Изменённые API, конфигурация и CLI отражены в документации.
- Команды и примеры проверены либо помечены как непроверенные.
- Внутренние ссылки и ссылки на файлы не ведут на несуществующие ресурсы.
- Устаревшие инструкции удалены или обновлены.
- Документация оформлена в соответствии со стилем проекта.
- Проверки документации завершились успешно.
- Изменения оформлены локальными git-коммитами.
- Worker получил список изменённых файлов, выполненных проверок и оставшихся ограничений.

### Запрещено

- Выдумывать API, команды, параметры или поведение системы.
- Скрывать ограничения и известные проблемы.
- Обновлять документацию только формально, без проверки соответствия коду.
- Удалять полезную документацию без замены или объяснения причины.
- Добавлять секреты, токены, пароли или реальные значения приватной конфигурации.
- Самостоятельно выполнять push в корневую ветку или удалённый репозиторий.
